SOFATracer traceId 透出 —— 端到端测试计划

Delta Plan ・ 2026-09-06 ・ Execution handoff execution-anchors/v1 ・ canonical 2026-09-06-traceid-propagation-e2e-test-plan.md ・ 执行结果 execution-report.html（其中记录了对 S1 第 ④ 条期望的执行期修正）

业务成果：工程师／agent 调用一个 SOFARPC facade 后，能用工具返回的 diagnostics.traceId 在 provider 日志里定位到这一次调用。

核心判据：provider 端 SOFATracer 的 server span 必须采用客户端生成的 traceId， 而不是自己新造一个。判据点在 RpcSofaTracer.serverReceived → saveSpanContextAndTags： 读 requestProps["rpc_trace_context"] 的 sofaTraceId；读不到则 spanContext == null， 服务端 buildSpan().start() 造新 id，客户端永远不知道。因此「两个 id 字符串相等」是修复生效与失效的分界线，不是近似指标。

正常链路

invoke / replay / call
   │ J1  NewTraceContext 生成 traceId
   │ J2  addTraceContext → requestProps["rpc_trace_context"]
   │ J3  bolt + hessian2 上线
   │ J4  SofaRpcSerialization 反序列化 + parseRequestHeader 合并（header 侧为空 → 不覆盖）
   │ J5  RpcSofaTracer.serverReceived 采纳 sofaTraceId → server span
   │ J6  tracelog/rpc-server-digest.log
   └ J7  diagnostics.traceId（成功与失败路径同样返回）

最高风险分支

  • J4 的覆盖风险：服务端会把 bolt header 里 rpc_trace_context. 前缀项合并进来。已核实客户端 header 不发该前缀，body 已有 map 时走 putAll(empty) 空操作，不会覆盖。
  • 静默降级：provider 未接 SOFATracer 时 map 被忽略且无任何失败信号（缺口 G1）。
  • 通道优先级：new_rpc_trace_context 优先级高于本次使用的老通道；sofarpc-cli 是链路起点不会携带，本地不可达（缺口 G3）。
